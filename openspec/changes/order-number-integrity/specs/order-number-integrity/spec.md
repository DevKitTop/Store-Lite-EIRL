# Delta for order-number-integrity

**Capability**: new — no `openspec/specs/order-number-integrity/spec.md` exists, so every requirement below is ADDED.
**Reality check**: DEV has 89 payments (6 `order_number IS NULL`, 83 already valid, 2 with printed `ticket_url`). PROD is empty. This change is forward-looking prevention; there is no production data to repair.

## ADDED Requirements

### W-P4 — Server-generated order number (root fix)

#### Requirement: P4-1 Server-side generation is authoritative

`orderNumber` MUST be generated by the server at the single `payments` insert site (`app/api/payment/charge/route.ts`). Any client-supplied `metadata.orderNumber` MUST be discarded and MUST NOT reach `payments.order_number` nor the persisted `metadata` jsonb.

- GIVEN a charge request carrying `metadata.orderNumber: "ORD-ATTACKER0000"`
- WHEN the payment is inserted
- THEN the stored `order_number` MUST differ from the supplied value and match the generator format
- AND the stored `metadata` MUST NOT contain an `orderNumber` key

#### Requirement: P4-2 Values are not derivable from wall-clock time

Generated values MUST carry at least 32 bits of non-time entropy, so a known purchase window does not reduce them to a feasible enumeration.

- GIVEN `Date.now()` is frozen and 100 values are generated
- WHEN the values are compared
- THEN at least 2 MUST be distinct (output is not a pure function of the clock)
- AND the candidate count for any 5-minute window MUST exceed 10^9

#### Requirement: P4-3 Millisecond collisions are impossible

- GIVEN 2 charges issued within the same millisecond
- WHEN both are inserted
- THEN their `order_number` values MUST differ
- AND a unique-constraint conflict MUST be retried, never surfaced to the buyer as a failed payment

#### Requirement: P4-4 Immutability after insert

`order_number` MUST NOT change once written.

- GIVEN a payment with `order_number = X`
- WHEN any update or idempotent replay runs
- THEN `order_number` MUST still be `X`
- AND a direct SQL `UPDATE` that sets `order_number` MUST be rejected

#### Requirement: P4-5 Database enforces NOT NULL and UNIQUE

`payments.order_number` MUST be `NOT NULL` and `UNIQUE` in every environment.

- GIVEN an insert without `order_number`
- WHEN it is attempted
- THEN the database MUST reject it
- AND a second insert reusing an existing value MUST be rejected

#### Requirement: P4-6 URL-safe, short, filename-safe format

Values MUST match `^ORD-[A-Za-z0-9_-]{8,20}$` and MUST NOT exceed 32 characters. The `ORD-` prefix MUST be retained so legacy and new values share one validator.

- GIVEN a newly generated value
- WHEN it is placed in the verify path segment, the ticket QR URL, and the ticket storage filename sanitizer `[^a-zA-Z0-9_-]`
- THEN all three MUST reproduce the value unchanged, with no substitution, truncation, or filename collision

#### Requirement: P4-7 Generation failure never persists null

- GIVEN generation throws
- WHEN the charge request is processed
- THEN the transaction MUST roll back and NO `payments` row MUST exist
- AND the response MUST be 5xx and the idempotency key MUST be completed with the failure, so the buyer is not permanently locked out

#### Requirement: P4-8 The Culqi-side label is reconciled

`app/api/payment/create-order/route.ts` MUST reuse the same shared generator and MUST NOT write its value into `payments.order_number` nor present it as the buyer's permanent order number.

- GIVEN an async Culqi order created via `create-order`
- WHEN the buyer later pays and `charge` inserts the payment
- THEN `payments.order_number` MUST be the value generated at insert, not the Culqi label

(Previously: an independent `ORD-<uuid slice>` generator, unrelated to the local identifier.)

#### Requirement: N1-1 No unusable auth path (W-N1 consequence)

After this change, no order may lack a working buyer auth path.

- GIVEN the change is deployed
- WHEN `SELECT count(*) FROM payments WHERE order_number IS NULL` runs
- THEN it MUST return 0
- AND every returned `order_number` MUST satisfy `lookupOrderSchema` and match exactly one row

### W-P5 — Single-row, ownership-scoped updates

#### Requirement: P5-1 No blind multi-row UPDATE keyed by orderNumber

Every `payments` write MUST be keyed by the row's primary key. `update-ticket` and `ticket/generate` MUST resolve `orderNumber` to exactly one row, enforce ownership on that row, then UPDATE by `payments.id`.

- GIVEN 2 rows sharing an `orderNumber` (legacy data)
- WHEN an owner of business A calls `update-ticket` with that number
- THEN only business A's row MUST be updated
- AND the UPDATE MUST affect exactly 1 row; 0 rows MUST return 404

#### Requirement: P5-2 The reprint flow keeps working

`POST /api/ticket/generate` MUST continue to accept `{orderNumber, forceRegenerate, trackingToken}`, reuse an existing `ticket_url` when regeneration is not forced, and never change `order_number`.

- GIVEN a payment with a `ticket_url` and no `forceRegenerate`
- WHEN a buyer presents a valid `trackingToken`
- THEN the existing `publicUrl` MUST be returned and the stored file MUST NOT be rewritten
- AND a buyer without a valid token MUST receive 401 and MUST NOT be able to overwrite the ticket
- GIVEN an owner forces regeneration
- WHEN the PNG is rendered
- THEN the QR MUST still encode `/{slug}/order/verify/{orderNumber}` and the storage object MUST keep the same filename

### Migration `0048_*`

#### Requirement: MIG-1 Backfill scope

The migration MUST assign values ONLY to rows where `order_number IS NULL`.

- GIVEN DEV 89 rows (6 NULL, 83 valid, 2 with `ticket_url`)
- WHEN the migration runs
- THEN exactly the 6 NULL rows MUST change
- AND the 83 existing values MUST remain byte-identical
- AND the 2 rows with `ticket_url` MUST NOT be renumbered, so their stored filenames stay resolvable

#### Requirement: MIG-2 Safe and idempotent

- GIVEN PROD with 0 rows
- WHEN the migration runs
- THEN it MUST succeed, backfill 0 rows, and leave the constraints in place
- GIVEN it has already been applied
- WHEN it is applied again
- THEN it MUST change 0 rows and MUST NOT alter any existing constraint or value

## Out of Scope

| Item                                | Why excluded                                       |
| ----------------------------------- | -------------------------------------------------- |
| Renumbering the 83 existing values  | Printed tickets and QR codes already embed them    |
| Renumbering the 2 `ticket_url` rows | Physical printed tickets would become unverifiable |
| `payments.status` handling          | W-P6, separate change                              |
| WhatsApp / YCloud items             | W-W1..W-W4, separate PR                            |
| Redis / Upstash rate limiting       | W-I1, needs infra                                  |
| Verify-page access gate             | Already shipped in PR #209                         |
| Migration journal fix               | Unchanged, separate concern                        |
